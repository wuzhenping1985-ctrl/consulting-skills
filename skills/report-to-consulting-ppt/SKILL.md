# Report To Consulting PPT

## Preferred Skill Route

For text-heavy report to editable PPT requests, prefer the dedicated `report-png-editable-ppt` skill. It owns the mandatory CODEX-PPT image deck -> local PNG extraction -> Presentations editable rebuild workflow and its approval gates. Use this skill only as a legacy/coordinating reference unless the user explicitly invokes it.

## User Standing Rule: No Skipping The PNG-To-Editable Pipeline

用户明确要求：凡是把文字报告、Word 报告、PDF 文字报告、研究报告、咨询报告、审计报告、战略报告、方案文本等“文字报告”转成 PPT，且最终需要可编辑 PPT 时，必须严格执行以下三步，任何一步都不许跳过：

1. 先使用 `codex-ppt` / CODEX-PPT 工作流生成图片式 PPT。
2. 将图片式 PPT 中的每页抽取出来，以 PNG 格式保存到电脑本地，按页序命名为 `slide_XX.png`。
3. 对这些 PNG 页面执行视觉拆解：把页面内容拆解成可放入 PPT 的独立元素，包括但不限于 PNG 图片局部、原生表格、单独文本框、形状、连接线、图标和图表；然后把拆解后的内容重新放入 PPT，使用 `presentations` 技能/运行时生成支持编辑的 PPT 内容。

This is the mandatory pipeline for text-report-to-editable-PPT requests. Do not directly build the final editable PPT from the source report, even if doing so seems faster. Do not route text-heavy report conversions through the older `image PPT -> PDF -> pdf-to-editable-ppt` pipeline unless the user explicitly asks for that older route in the same request. The image deck and saved PNG slides are required intermediate artifacts. The final editable deck must be rebuilt from the PNG visual reference by decomposing each page into editable presentation elements and generating the PPT through `presentations`.

## Goal

Turn a text-heavy PDF or Word report into an editable consulting PowerPoint deck through a three-stage pipeline: first synthesize the report into a visually coherent image-based deck with CODEX-PPT, then extract/save the image deck slides as local PNG files, then use those PNG pages as visual references to rebuild the final deck as editable PowerPoint elements with the `presentations` workflow.

Use `pdf-to-editable-ppt` directly only for PPT-like PDF page reconstruction. Use this skill as the coordinator for text-heavy Word/PDF sources that must become editable PPT.

## Routing Rules

Choose exactly one route at the start:

- **PPT-like PDF route**: if the input is already close to a slide deck and the user asks to convert it one-to-one or faithfully into editable PPT, do not use this report synthesis pipeline. Use `pdf-to-editable-ppt` directly.
- **Text-heavy source route**: if the input is a Word/DOCX, text-heavy PDF, long report, strategy document, audit report, proposal, research report, or notes, and the user asks for editable PPT, use the CODEX-PPT -> PNG extraction -> Presentations editable rebuild pipeline below.

If the input type is ambiguous, inspect the source before choosing: a slide-like 16:9/4:3 PDF with one visual page per slide goes to `pdf-to-editable-ppt`; a prose-heavy document with sections, paragraphs, long tables, or report pages goes through the three-stage text-heavy route.

For both routes, the final user-facing PPTX must use the CIIC consulting template/style system. The PPT-like PDF route must use `pdf-to-editable-ppt` and its bundled `assets/default-template.pptx`; the text-heavy source route must end with the Presentations editable rebuild stage. An intermediate image-based PPTX generated by Codex PPT is not the final deliverable and must not be delivered as the only PPTX unless the user explicitly asks for a raw image-deck companion output.

## Three-Stage Text-Heavy Route

For text-heavy Word/PDF sources, run these stages in order:

1. **Synthesize with Codex PPT**
   - Read `references/codex-ppt-image-workflow.md`.
   - Use the Codex PPT workflow to turn the source material into a visually coherent image-based PPTX.
   - Keep the Codex PPT planning discipline: outline, visual style, image backend, one sample slide, full slide generation, QA, and speaker notes when useful.
   - The image-based PPTX is an intermediate artifact, not the final deliverable.

2. **Extract and save slide PNGs**
   - Extract the image-based PPTX slides to PNG files in strict slide order, or use the CODEX-PPT `origin_image/slide_XX.png` files directly when they already exist.
   - Save the PNG files locally on the computer and preserve the originals. Name final visual references as `slide_01.png`, `slide_02.png`, etc.
   - Verify every expected slide PNG exists, is readable, is 16:9, and visually corresponds to the image-based PPT slide order before continuing.

3. **Decompose PNGs and rebuild editable PPT with Presentations**
   - Treat each PNG as the visual source of truth.
   - Decompose each page into editable PPT-ready elements: local PNG crops for inherently raster elements, native text boxes for text, native tables for tabular regions, native shapes/connectors/icons for diagrams, and native charts where practical.
   - Rebuild the final deck with `presentations` / the Presentations runtime so that the delivered PPTX supports editing of text, tables, shapes, and diagrams wherever feasible.
   - On Windows, ensure the `HOME` environment variable points to the user profile directory (for example `C:\Users\A`) before running Presentations artifact-tool scripts; otherwise the runtime may look for `@oai/artifact-tool` under the current working directory instead of the bundled Codex runtime.
   - Do not place each full-slide PNG as the final slide content. Full-slide PNGs are visual references only; use tightly cropped PNG fragments only for inherently raster content.
   - Run the appropriate PPTX audit and visually inspect rendered slides when possible.

Final delivery is the editable PPTX from stage 3. Report the intermediate image PPTX and PNG directory paths as supporting artifacts.

## Required Style Contract

Build the final deck with the CIIC/Yuexiu consulting visual system while using `presentations` for the final editable PPT generation:

- Use `assets/base-ciic-yuexiu-template.pptx` as the base deck unless the user provides a newer explicit template.
- Follow `references/yuexiu-style-guide.md` for title sizes, colors, page geometry, footer/page marker, section pages, catalog pages, and content-page spacing.
- Use Microsoft YaHei/微软雅黑 for normal Chinese text. Use Impact only for large standalone KPI numerals when appropriate.
- Content-page titles default to 24pt bold; reduce to 22pt or 20pt only when necessary.
- Key-point lead text is 16pt. Normal body text is 14pt. Dense table/support text is 12pt preferred; 10-11pt only when unavoidable.
- Enable automatic text wrapping for every text box, shape text frame, and table cell. Do not use manual line breaks as the primary way to force wrapping unless a deliberate phrase break improves readability.
- Keep all main body content between the upper and lower blue rules. Do not cover the footer, page marker, or rules.
- Use the page number/page marker already built into the base template. Do not draw, copy, or add any extra right-bottom page number or orange page-marker shape on body slides.
- Keep the cover formal and uncluttered. The cover should contain only the report title, subtitle/topic/client/project, date/team/source line where available, and template-provided brand/background elements. Do not add executive-summary claims, "core thesis" labels, KPI cards, diagnostic boxes, charts, or model-library framework elements to the cover unless the user explicitly asks for an analytical cover.
- Keep the blue-led corporate palette: primary `#1C55FE`, secondary `#547FFE`, light blues `#8DAAFE` / `#B3D4FE` / `#CFDBFF`, rule/link blue `#0042FF` / `#126BF7`, dark text `#383838`, small orange accent `#FF4200`.
- No shadows. No decorative template-watermark text. No instructional pages from the model library.

## Management Consulting PPT Design Rules

Apply these rules when synthesizing text-heavy reports into consulting PPT storylines, generating the intermediate CODEX-PPT image deck, and rebuilding the final editable deck:

- Overall positioning: prioritize clear logic, scan-friendly hierarchy, professional credibility, and systematic structure over decoration. Use a white canvas, blue-led brand system, light-gray/blue modules, and a small orange accent.
- Page system: use 16:9 widescreen. Content pages should be white-based; reserve full blue/visual backgrounds for cover, chapter, summary, or back-cover pages. Keep stable footer/logo/URL/page-marker placement from the CIIC/Yuexiu template.
- Typography: use Microsoft YaHei/微软雅黑 for Chinese and Arial for English/numbers unless a user template overrides it. Use bold action titles, regular body copy, and bold/color only for keywords.
- Font hierarchy: cover title 28-36pt; body-page title 20-24pt, with the CIIC/Yuexiu default at 24pt; module title 16-18pt; secondary label 14-16pt; body 12-14pt; notes and footnotes 8-10pt; large numbers/step ids 28-36pt.
- Color use: primary blue for titles, navigation, main flows, arrows, icons, and key labels; pale blue/light gray for module backgrounds and grouping; dark gray `#383838` for normal text; orange `#FF4200` only as small page markers, nodes, tags, or highlights. Use red only for risks, pain points, or strong warnings.
- Layout grammar: each content slide should have one message-led title, an optional one-sentence lead, and one dominant visual structure. Prefer frameworks, matrices, processes, cycles, roadmaps, issue trees, comparison grids, KPI cards, and architecture diagrams over plain bullet lists.
- Action titles: convert source headings into conclusion-oriented titles. The title should state the page's judgment, implication, or recommendation, not merely name the topic.
- Diagram and frame rules: use rectangles, low-radius rounded rectangles, arrows, dotted boundary boxes, circular step ids, and native-looking line icons. Same-level cards must share size, fill, border, and typography. Important relationships use solid lines; auxiliary boundaries use dotted lines.
- Line rules: use 0.5-0.75pt for ordinary borders, 1.0-1.5pt for emphasized borders, and 1.5-3pt for main process arrows. Do not mix many line styles on one page.
- Density rules: one core message per slide; 3-6 major modules per content page; 2-4 short lines per module. If there are more than six modules, group them or split the slide. Keep dense slides structured, not text-stacked.
- Emphasis rules: highlight 1-3 keywords per text block. Use blue bold for strategic keywords, red/orange only for pain points or alerts, and large numerals for steps or metrics. Do not make a page look colorful by emphasizing everything.
- Navigation rules: for full consulting decks, use a top or side chapter navigation when useful. Keep section names short, gray for inactive sections, and primary blue for the current section.
- Avoid: decorative gradients, heavy shadows, large dark navy panels on body pages, generic stock imagery, repeated same-card layouts on every slide, centered body paragraphs, text outside frames, duplicated text overlays, leftover placeholders such as `Sample`, raw model-library sample text, and full-slide generated images as the final editable deliverable.

## Source-To-Deck Workflow

1. Read and understand the source report.
   - For Word/DOCX, extract headings, paragraphs, tables, figures, notes, and appendices.
   - For PDF, extract text/tables/images and render pages for visual checking when needed.
   - Identify the report type: strategy, diagnosis, planning, proposal, research, audit, implementation plan, operating analysis, or executive brief.

2. Create a slide storyline.
   - Convert document headings into a deck outline: cover, catalog, executive summary, section dividers, body slides, conclusion/next steps, back cover.
   - Do not create one slide per source page by default. Merge, split, or reorder content to make slide logic clear.
   - Use action titles: each slide title should state the conclusion or message, not merely repeat a source heading.
   - Keep source facts faithful. If the source does not support a claim, do not invent it.
   - For substantial decks, define each slide with: slide number, action title, 3-5 key points, slide role, visual idea, candidate model/layout, required source assets, and speaker-note intent.
   - Ask for outline confirmation when the user requests staged approval, when the deck depends on user-provided source images/figures whose slide mapping is uncertain, or when the requested audience/objective is ambiguous. Otherwise, create the outline as an internal or saved planning artifact and proceed.

3. Choose slide types and model diagrams.
   - Read `references/model-selection-guide.md` before choosing model slides.
   - Use `assets/model-library/*.pptx` as the business-blue Microsoft YaHei model library.
   - Prefer adapting a suitable model-library page for each正文/content slide whenever the report logic reasonably fits one. Use a plain template-only content page only when no library layout fits the content.
   - Skip model-library instruction, copyright, QR-code, font-installation, and color-change pages.
   - Select framework models by content logic, not by visual preference: strategy house for goal/pillar/foundation, platform for layered capability systems, radial for hub-and-spoke ecosystems, cycle for closed-loop management, business process for end-to-end workflows, timeline for phased roadmaps.
   - Use `page-design-collection-20160624.pptx` for generic page structures such as relationship diagrams, two-item comparisons, multi-option layouts, and visual composition references when the dedicated business framework modules are not a good fit.
   - Vary slide composition according to page semantics: cover, catalog, section divider, executive summary, diagnosis, evidence, comparison, framework, process, roadmap, recommendation, risk/control, and appendix pages should not all share one repeated card layout.

4. Build editable slides.
   - Start from the CIIC/Yuexiu base template and add slides using cover/catalog/section/content/back-cover roles.
   - Treat cover, catalog, section dividers, content pages, and back cover as different slide roles. Model-library frameworks and dense proof objects belong on content pages, not on the cover, catalog, or back cover unless explicitly requested.
   - Recreate or adapt selected model diagrams as editable PowerPoint shapes, connectors, tables, and text. Copy native shapes from the model deck only when they remain editable and visually compatible.
   - Replace all model placeholder text with source-specific content. Do not leave generic example labels, instructional notes, template logos, QR codes, or model copyright text.
   - Use native tables for tabular evidence and native charts/diagrams for synthesized logic.
   - Keep text inside shapes or cells; do not overlay duplicate text for emphasis.
   - Set all text-containing objects to automatic wrapping, then size the object and font so wrapped text remains readable and does not overflow.
   - Preserve the base template's built-in footer/page number. If a copied model slide brings its own page number, delete the copied one and keep only the base-template page marker.
   - Use the content area actively on body/content pages. Body pages should not leave excessive blank space; enlarge diagrams/tables/text groups or choose a richer model layout when the slide looks sparse. Keep breathing room around groups, but avoid empty half-page layouts unless the message intentionally requires it. Do not apply this density rule to the cover, catalog, section dividers, or back cover.
   - When drawing numeric charts with native shapes, use one explicit scale for all marks that are meant to be compared. Do not mix per-series or per-row maximums unless the chart is clearly separated and labeled as index/relative scale.
   - Before finalizing any manually built bar, line, KPI gauge, waterfall, or proportional diagram, verify the visual ordering matches the numbers: a larger number must never render as a shorter/smaller mark than a smaller number within the same comparison set.
   - Keep any saved planning artifacts synchronized with the final deck when practical: outline, source-asset mapping, and speaker notes should reflect the final slide order and messages.

5. Verify and polish.
   - Render the deck to images/PDF when possible and inspect slides visually.
   - Run `scripts/audit_pptx.py` on the final PPTX.
   - Check every slide for title size, body readability, page bounds, text overlap, content/rule collisions, footer/page marker clearance, and template consistency.
   - For every chart-like visual, perform a data-to-visual consistency check after render: compare the source numbers against bar lengths, line positions, segment widths, ranks, percentages, axis labels, and callout values. Fix any chart where the rendered visual implies a different relationship than the data.
   - Check visual identity across the whole deck: same palette, typography, icon/diagram language, and spacing rhythm, with page layouts varied by slide role.
   - If speaker notes were requested or are useful for delivery, write concise notes by slide using `Slide N` headings or PowerPoint notes.

## Slide Logic Defaults

- Cover: report title, client/project/topic, date/team where available. Keep it formal; do not place diagnostic conclusions, "core thesis" callouts, KPI cards, evidence boxes, charts, or model-framework elements on the cover unless the user explicitly requests this.
- Catalog: 3-6 major sections, not every source heading.
- Executive summary: 3-5 key conclusions or recommendations.
- Diagnosis/problem slides: use evidence table, issue tree, comparison matrix, or KPI cards.
- Framework/design slides: use a suitable model from the bundled model library.
- Implementation slides: use business-process or timeline models.
- Standard正文/content slides: first look for a model-library layout that fits the message, including generic designs from `page-design-collection-20160624.pptx`, before falling back to a plain text/table layout.
- Recommendations: use grouped action cards, priority matrix, roadmap, or responsibility table.
- Appendix: preserve detailed source tables only when needed; otherwise summarize.

## Mandatory Quality Rules

- Final output must be `.pptx`.
- The final user-facing PPTX must be based on the CIIC consulting template. Do not deliver a blank-deck assembly or raw generated-image PPTX as the only final PPT unless the user explicitly asks for an image-only companion deck.
- The deck must be editable: text, tables, diagrams, and connectors should be native objects wherever feasible.
- Text boxes, shape text frames, and table cells must have automatic text wrapping enabled.
- Body slides must not contain manually added duplicate right-bottom page numbers or extra orange page-marker shapes.
- The cover must not contain body-slide analysis objects such as conclusion banners, "core thesis" labels, KPI cards, diagnostic boxes, charts, evidence tables, or model-library framework diagrams unless the user explicitly requested an analytical cover.
- The deck must use the CIIC/Yuexiu style system, not the raw visual style of the source report.
- The model library is a structure source, not a content source. Never keep model-library sample business text unless the user explicitly requests it.
- Prefer model-library page structures over blank layouts when they improve clarity and density. Avoid overpacking slides, but also avoid excessive正文页留白; split dense report sections into multiple message-led slides and scale sparse pages up to use the available content area.
- The deck must have one coherent visual identity while varying page composition by slide role. Avoid producing every content slide as the same repeated card layout.
- Numeric visuals must be truthful at a glance. If values are directly comparable, their bars/segments/markers must share the same scale and preserve the correct visual ordering. Label any normalized or indexed view explicitly; otherwise use absolute scale.
- Keep all important source figures/tables traceable: if a key source table is simplified, preserve the original detail in notes or appendix when useful.
- Do not use screenshots as the main slide content except for non-editable source images, maps, or screenshots that genuinely need raster treatment.
- Do not use full-slide generated images for the default editable consulting deliverable. Full-slide-image PPTX output is allowed only in the explicit image-based companion mode.
